# Backend architecture, database, auth and hosting options for a public research simulator (status as of 2026-10-15)

Scope: a small-team, near-zero-cost backend behind a GitHub Pages frontend that needs sign-up/login, saved runs and scenarios, shareable run links, a community gallery/leaderboard, a job queue for second-to-minute Python discrete-event simulations with small policy inference, a provenance/audit trail, and a public read-only API. All prices/limits below were read from the cited pages on 2026-10-15 unless noted; third-party sources are flagged. Web search budget ran out near the end, so a few corroborations (Hetzner April-2026 price change, Oracle cut announcement date, Turso/Supabase deal date) rest on single sources and are flagged in Gaps.

## Q1. Which Python stack (framework + job handling + progress streaming) is defensible as "serious" yet cheap for a solo maintainer?

### Takeaway
FastAPI (ASGI) with a Redis/Valkey-backed queue (RQ) or, at the very start, a single DB-backed worker process, plus `sse-starlette` for Server-Sent Events progress, is the lowest-maintenance "serious" stack; Django 6.0 is the credible alternative mainly because `django-allauth` ships ORCID login and passkeys out of the box, but its new built-in Tasks framework still needs a third-party worker. `arq` should be avoided for new work (maintenance-only), and FastAPI's own `BackgroundTasks` is explicitly not for heavy compute.

### Cited Findings
- FastAPI docs on `BackgroundTasks`: "If you need to perform heavy background computation and you don't necessarily need it to be run by the same process (for example, you don't need to share memory, variables, etc), you might benefit from using other bigger tools like Celery." They "tend to require more complex configurations, a message/job queue manager, like RabbitMQ or Redis, but they allow you to run background tasks in multiple processes, and especially, in multiple servers." `BackgroundTasks` is for "small background tasks (like sending an email notification)" and runs "after returning a response." — [FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)
- RQ (Redis Queue): "simple Python library for queueing jobs and processing them in the background with workers", "backed by Redis/Valkey"; current release 2.12.0 (Aug 30, 2026); requires Python >=3.10 and "Redis >= 5 or Valkey >= 7.2"; RQ 2.5+ includes built-in interval and cron scheduling (`enqueue_at`, `enqueue_in`, `rq cron`). — [PyPI: rq](https://pypi.org/project/rq/)
- Celery: "Distributed Task Queue"; current 5.6.3 released Mar 26, 2026; Python >=3.9; message transports "RabbitMQ, Redis, Amazon SQS, Google Pub/Sub". — [PyPI: celery](https://pypi.org/project/celery/)
- arq: PyPI states the project "is in maintenance only mode, see #510"; latest confirmed version 0.28.0. — [PyPI: arq](https://pypi.org/project/arq); mirrored in the docs: "In maintenance only mode" — [arq docs](https://docsearch.algolia.com/mcp/docs/repo/python-arq/arq)
- Django 6.0 Tasks framework (new, released Dec 2025/Jan 2026 coverage): "Django's Tasks framework makes it easy to define and enqueue such work. It does not provide a worker mechanism to run Tasks. The actual execution must be handled by infrastructure outside Django, such as a separate process or service." "Django comes with built-in backends, but these are for development and testing only." "Production systems should rely on backends that supply a worker process and a durable queue implementation." Task args/returns "are serialized to JSON". — [Django 6.0 Tasks docs](https://docs.djangoproject.com/en/6.0/topics/tasks/); critical review titled "Django 6.0 Tasks: a framework without a worker" — [loopwerk.io](https://www.loopwerk.io/articles/2026/django-tasks-review/); InfoQ notes the "minimal default configuration has drawn criticism" — [InfoQ](https://infoq.com/news/2026/01/django-6-release)
- Server-Sent Events for FastAPI: `sse-starlette` 3.5.0 (Sep 28, 2026), "Production ready Server-Sent Events implementation for Starlette and FastAPI following the W3C SSE specification"; `EventSourceResponse` takes an async generator, has "Automatic client disconnect detection", `ping` keep-alive default 15 s, `send_timeout` to detect dead connections; Python >=3.10. — [PyPI: sse-starlette](https://pypi.org/project/sse-starlette/)
- Rate limiting for FastAPI: `slowapi` is "A rate limiting library for Starlette and FastAPI adapted from flask-limiter", wraps the `limits` library, supports "redis, memcached and memory backends"; caveat: "websocket endpoints are not supported yet" and the `request` argument must be passed explicitly. — [GitHub: laurents/slowapi](https://github.com/laurents/slowapi)
- Django's auth ecosystem advantage: `django-allauth` includes an ORCID provider that "should work out of the box provided that you are using the Production ORCID registry and the public API" (`BASE_DOMAIN` default `orcid.org`, `MEMBER_API` default `False`). — [allauth ORCID provider](https://docs.allauth.org/en/latest/socialaccount/providers/orcid.html); WebAuthn security-key and passkey login landed in the 64.x line (64.2.1, 2024-09-05), enabled via `"webauthn"` in `MFA_SUPPORTED_TYPES` and `MFA_PASSKEY_LOGIN_ENABLED`, with the `fido2` dependency from `pip install "django-allauth[mfa]"`. — [allauth WebAuthn docs](https://django-allauth.readthedocs.io/en/stable/mfa/webauthn.html); [allauth release notes](https://django-allauth.readthedocs.io/en/stable/release-notes/recent.html)

### Inferences
- For second-to-minute CPU-bound simulation jobs, the queue must run in a separate worker process (not FastAPI `BackgroundTasks`), otherwise one simulation blocks the API event loop/worker. RQ is the smallest credible step up: one Redis/Valkey instance, one `rq worker` process, JSON-serialisable job payloads, built-in result/failed registries. Celery is defensible but adds config surface a solo maintainer does not need at this scale.
- A "zero extra service" starting point is a single worker process polling a `jobs` table in the same SQLite/Postgres database (status + `SELECT ... WHERE status='queued' ORDER BY created_at LIMIT 1` with a row-level claim); it avoids Redis entirely and is enough for a few concurrent users. Keep the job interface narrow (enqueue(run_id) / status(run_id)) so swapping in RQ later is mechanical.
- Progress streaming: SSE is preferable to WebSockets here because the flow is one-directional (server to browser), works through plain HTTP/HTTPS and CDNs, auto-reconnects in the browser `EventSource` API, and the chosen hosts' cold-start/sleep behaviours are easier to tolerate. Note `slowapi` cannot rate-limit WebSocket endpoints, another reason to prefer SSE + polling fallback.
- Flask was not separately researched (see Gaps); as a WSGI-first framework it would need extra pieces (flask-sock, gevent/eventlet, or an ASGI bridge) for SSE/WebSockets that FastAPI and Django (ASGI) have natively, so it is not recommended for this feature set.
- Django is the right fallback if auth breadth (ORCID + GitHub + passkeys + email flows with one library) matters more than API ergonomics; FastAPI is the right default if the public JSON API, OpenAPI docs and typed Pydantic schemas for run records are the product.

- Did not verify current Django-side production Tasks backends (e.g., django-tasks-db or similar) by name; only the official statement that third-party backends are required.

## Q2. Database: when is SQLite (WAL) enough vs PostgreSQL; append-only run logs; JSON columns; content-addressed result files

### Takeaway
SQLite in WAL mode on a single host is sufficient for this product's expected traffic by SQLite's own guidance (fewer than ~100K hits/day, one writer at a time, all processes on the same machine), and Litestream 0.5 (with the new Python-installable VFS) now gives cheap continuous off-box replication and point-in-time restore; move to Postgres only if you need multiple hosts, many concurrent writers, or a managed DB (Neon/Supabase free tiers exist but have scale-to-zero/pausing behaviour that hurts a public site).

### Cited Findings
- SQLite appropriateness: "SQLite works great as the database engine for most low to medium traffic websites (which is to say, most websites)." "Generally speaking, any site that gets fewer than 100K hits/day should work fine with SQLite." "The 100K hits/day figure is a conservative estimate, not a hard upper bound. SQLite has been demonstrated to work with 10 times that amount of traffic." "SQLite does not compete with client/server databases. SQLite competes with fopen()." Client/server is better when "many threads and/or processes need to write the database at the same instant (and they cannot queue up and take turns)", when "many client programs sending SQL to the same database over a network", or when the site "is write-intensive or is so busy that it requires multiple servers". "SQLite supports an unlimited number of simultaneous readers, but it will only allow one writer at any instant in time." — [SQLite: Appropriate Uses](https://www.sqlite.org/whentouse.html)
- WAL mode: "WAL provides more concurrency as readers do not block writers and a writer does not block readers. Reading and writing can proceed concurrently." "since there is only one WAL file, there can only be one writer at a time." "All processes using a database must be on the same host computer; WAL does not work over a network filesystem." Applications "should be prepared for" `SQLITE_BUSY`. Auto-checkpoint at 1000 WAL pages by default; enable with `PRAGMA journal_mode=WAL;`. — [SQLite: WAL](https://www.sqlite.org/wal.html)
- JSON in SQLite: "The JSON functions and operators are built into SQLite by default, as of SQLite version 3.38.0 (2022-02-22)." "Beginning with version 3.45.0 (2024-01-15), SQLite allows its internal 'parse tree' representation of JSON to be stored on disk, as a BLOB, in a format that we call 'JSONB'." `->` and `->>` operators available since 3.38.0; `json_extract()` returns SQL-typed scalars for single paths. — [SQLite: JSON Functions](https://www.sqlite.org/json1.html)
- Litestream v0.5.0 (Fly.io post, Oct 2025): Litestream "runs as a sidecar process in the background, alongside unmodified SQLite applications"; 0.5 introduces the LTX file format (transaction-based, per-page compression with an index), a compaction hierarchy (Level 1 = 30-second window, Level 2 = 5-minute, Level 3 = hourly), lets you "restore a SQLite database to any point in time" using "only a dozen or so files on average"; one replica destination per database; CGO removed in favour of `modernc.org/sqlite`; backends: S3, Google Cloud Storage, Azure Blob Storage, NATS JetStream; the LiteFS (FUSE) detour was abandoned because users preferred Litestream; a VFS for read replicas was announced as the next major feature. — [Fly.io: Litestream v0.5.0 is Here](https://fly.io/blog/litestream-v050-is-here/); Simon Willison's note on the release — [simonwillison.net 2025-10-03](https://feeds.simonwillison.net/2025/Oct/3/litestream/)
- Litestream VFS for Python: `litestream-vfs` 0.5.17 (Aug 31, 2026) "bundles the Litestream VFS shared library so you can load it directly into a Python sqlite3 connection" via `litestream_vfs.load(conn)`; Linux x86_64/aarch64 and macOS; Development Status classifier "4 - Beta"; Apache-2.0. — [PyPI: litestream-vfs](https://pypi.org/project/litestream-vfs/); release notes (third-party mirror) list `pip install litestream-vfs` and "PRAGMA-based time travel for querying historical database states" and note "Windows is NOT an officially supported platform" — [newreleases.io v0.5.14](https://newreleases.io/project/github/benbjohnson/litestream/release/v0.5.14), [v0.5.3-beta1](https://newreleases.io/project/github/benbjohnson/litestream/release/v0.5.3-beta1)
- Content-addressed storage reference model: "Git is a content-addressable filesystem... at the core of Git is a simple key-value data store... you can insert any kind of content into a Git repository, for which Git will hand you back a unique key you can use later to retrieve that content." The key is the SHA-1 "of the content you're storing plus a header". — [Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- Managed Postgres free tiers (details in Q4): Neon Free = 1 GB storage/project, 100 CU-hours/project/month, "Scale to zero: After 5 min; cannot be turned off", compute suspended when CU-hours run out — [Neon pricing](https://neon.com/pricing); Supabase Free = "500 MB database size", "Limit of 2 active projects", "Free projects are paused after 1 week of inactivity" — [Supabase pricing](https://supabase.com/pricing); Render free Postgres "Fixed at 1 GB", "expire 30 days after creation" with a 14-day grace period then deletion — [Render free tier](https://render.com/docs/free)
- Hosted SQLite (Turso) Free: 100 databases, 5 GB storage, 500 M rows read/month, 10 M rows written/month, 3 GB monthly syncs, 1-day point-in-time restore; Developer plan $4.99/month (9 GB, 2.5 B reads, 25 M writes, 10-day PITR). The pricing page carries a 2026 banner: "Turso is joining Supabase to give every agent its own database". — [Turso pricing](https://turso.tech/pricing)

### Inferences
- Fit test for SQLite here: one API process + one worker process on the same VM/machine (satisfies "same host"), writes are short (job status updates, run-record inserts) and can "take turns", and public traffic is read-dominated (gallery, run pages, read-only API). Set `PRAGMA journal_mode=WAL`, `PRAGMA synchronous=NORMAL`, a `busy_timeout` of a few seconds, and keep write transactions tiny. Run Litestream as a sidecar replicating to any S3-compatible bucket (e.g., Hetzner Object Storage, Cloudflare R2, Backblaze B2) for disaster recovery and PITR.
- Postgres triggers: a second host (e.g., separate worker box), >1 concurrently writing process you cannot serialise, need for row-level locks across workers, or a desire for a managed backup/HA story you do not run yourself. Of the free managed options, Neon's 5-minute scale-to-zero means first-request latency after idle; Supabase's 7-day pause is a hard blocker for a public site unless something pings it; Render's free Postgres is a 30-day trial in practice.
- Schema pattern (works identically on SQLite and Postgres via SQLAlchemy): `runs` table with immutable provenance columns (see Q6) + a `result_summary` JSON column (SQLite JSON/JSONB or Postgres JSONB) for small leaderboard-relevant metrics; `run_events` append-only table `(run_id, seq, ts, event_type, payload_json)` for status transitions and progress (never UPDATE/DELETE rows; the current state is derived or cached); large result files (traces, per-tick logs, policy weights) stored on disk/object storage under `blobs/<sha256[:2]>/<sha256>` with the hash recorded in the run row. This is the Git object-store model and gives free deduplication (identical scenario files/policy weights stored once) and tamper evidence (a result file is valid iff its hash matches).
- Event-sourcing the whole system is overkill; an append-only `run_events` log plus immutable `runs` rows gives the audit trail researchers care about without the complexity of rebuilding state from events.
- JSON columns: keep queryable/sortable fields (score, duration, scenario_id) as real columns or indexed expression columns; put the long tail of metrics in JSON. SQLite's `->>` makes this ergonomic since 3.38; ensure the host Python's bundled SQLite is >=3.38 (3.45 for JSONB).

- No benchmark source was gathered quantifying SQLite throughput specifically for this write pattern; the 100K hits/day figure is SQLite's generic guidance.
- Did not verify which SQLite version ships with the Python builds on each host (matters for JSONB).

## Q3. Auth: which approach gives academics the least friction while staying secure, what would "ORCID login" take, and which Python libraries implement it?

### Takeaway
Offer ORCID and GitHub OAuth/OIDC login as the primary paths (ORCID Public API credentials are free for non-commercial individual use and provide an authenticated ORCID iD, which is also the ideal author identifier on run records), plus email magic links as the no-account fallback; if you keep passwords at all, hash with Argon2id at OWASP's 19 MiB/t=2/p=1 minimum via `argon2-cffi`. Use server-side sessions (opaque IDs in HttpOnly cookies, or opaque bearer tokens looked up server-side) rather than stateless JWTs, and add passkeys later (py_webauthn or django-allauth) rather than at launch.

### Cited Findings
- ORCID Public API client registration: "Public API credentials are tied to an individual's ORCID record and cannot be transferred to another person." The Public API "is free for non-commercial use by individuals" (non-commercial = no re-use fees and not used "in connection with any revenue-generating product or service"). "Organizational API credentials are available to organizations that support ORCID through a paid membership subscription." Steps: sign in, Developer Tools, agree to Public API ToS, enter Name/Application URL/Description, add redirect URIs, generate client ID/secret. "Only HTTPS URIs are accepted in production"; registered domains must exactly match including subdomains. Rate limits: Public (registered) 12 req/sec, 40 burst, 100k reads/day per Client ID; Anonymous 25k reads/day per IP; Member 24 req/sec, no quota. Sandbox registration at sandbox.orcid.org works the same way. — [ORCID: Registering a Public API client](https://info.orcid.org/documentation/integration-guide/registering-a-public-api-client/)
- ORCID sign-in flows: "For sign-in, there are two options: 3 legged OAuth (for long lived update permissions) and Implicit OAuth (for read-only short term permissions)"; ORCID "will only send authenticating users to URIs registered by the client". — [ORCID: Get an authenticated ORCID iD](https://info.orcid.org/documentation/integration-guide/api-tutorial-get-and-authenticated-orcid-id/)
- Authlib 1.9.1: "The ultimate Python library in building OAuth and OpenID Connect servers and clients"; client integrations for Requests, HTTPX, Flask, Django, Starlette and FastAPI; OAuth 1.0, OAuth 2.0, OpenID Connect, JOSE (JWS/JWE/JWK/JWT); "Get a commercial license at authlib.org" (dual licensing). — [Authlib docs](https://docs.authlib.org/en/latest/)
- django-allauth ORCID provider "should work out of the box provided that you are using the Production ORCID registry and the public API"; `SOCIALACCOUNT_PROVIDERS = {'orcid': {'BASE_DOMAIN': 'sandbox.orcid.org', 'MEMBER_API': True}}` for other environments. — [allauth ORCID](https://docs.allauth.org/en/latest/socialaccount/providers/orcid.html)
- Passwords (OWASP): "Use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism." Equivalent sets: m=47104 (46 MiB) t=1 p=1; m=19456 (19 MiB) t=2 p=1; m=12288 t=3; m=9216 t=4; m=7168 t=5. scrypt "should be used when the former is not available" (N=2^17, r=8, p=1); bcrypt "should only be used for password storage in legacy systems", work factor minimum 10, enforce a 72-byte max. A pepper "can provide additional defense in depth" but must be stored outside the DB (vault/HSM). — [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- `argon2-cffi` 25.1.0 (Jun 3, 2025), "Argon2 for Python"; the documented example hash shows `m=65536,t=3,p=4` (page does not label these as defaults). — [PyPI: argon2-cffi](https://pypi.org/project/argon2-cffi/)
- Magic-link token hygiene (OWASP password-reset guidance, same mechanism): tokens must be "Generated using a cryptographically secure random number generator", "Long enough to protect against brute-force attacks", "Single use and expire after an appropriate period", "Invalidated after they have been used", "Stored in a secure manner, as discussed in the Password Storage Cheat Sheet"; "Ensure that the URL is using HTTPS"; set Referrer-Policy `no-referrer`; "Implement appropriate protection to prevent users from brute-forcing tokens in the URL, such as rate limiting"; "Don't rely on the Host header while creating the reset URLs"; "Return a consistent message for both existent and non-existent accounts" and "consistent amount of time". — [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
- Sessions vs tokens (OWASP): "Session identifiers must have at least 64 bits of entropy"; self-generated IDs "at least 128 bits", server-side tokens "prefer 160 bits or more"; "Session cookies must explicitly set SameSite=Strict (preferred) or SameSite=Lax"; `Secure`, `HttpOnly`, no `Domain` attribute, restrictive `Path`; "All sessions should implement an absolute timeout" (example 4-8 hours), idle timeouts "15-30 minutes for low risk applications"; "Do not store authentication tokens, session IDs, JWTs, refresh tokens, or any credential in" localStorage/sessionStorage because "These APIs are accessible to any JavaScript executing in the origin"; recommended: "Use HttpOnly; Secure; SameSite=Strict cookies (preferred) or a Backend-for-Frontend (BFF) pattern"; "deleting a cookie alone does not invalidate a stolen copy of the session ID". — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- Passkeys in Python: `py_webauthn` (PyPI package `webauthn`) is framework-agnostic with four core functions (generate/verify for registration and authentication); `fastapi-passkeys` is a small third-party wrapper (v0.1.2, ~280 downloads/month) depending on `webauthn`. — [This Week at Passkeys: FastAPI Passkeys, 9 WebAuthn server libs compared](https://passkeys.substack.com/p/fastapi-passkeys-9-webauthn-server); [PyPI: webauthn](https://pypi.org/project/webauthn/1.5.0); [pypistats: fastapi-passkeys](https://pypistats.org/packages/fastapi-passkeys)
- Hugging Face as a third IdP for ML researchers: Spaces can enable OAuth with `OPENID_PROVIDER_URL` and discovery at `https://huggingface.co/.well-known/openid-configuration`, scopes "openid profile". — [HF Spaces overview](https://huggingface.co/docs/hub/spaces-overview)

### Inferences
- Least-friction order for academics: (1) "Sign in with ORCID" (every active researcher has one, and it yields the exact identifier you want to stamp on runs and in citations), (2) "Sign in with GitHub" (the audience that will clone the simulator), (3) email magic link (no password to remember; also doubles as email verification). Passwords are optional; if present, Argon2id via `argon2-cffi` (or Django's built-in Argon2 hasher in a Django stack). Passkeys are a nice later addition; `django-allauth` makes them nearly free in a Django stack, while in FastAPI you wire `py_webauthn` into two endpoints each for registration and login.
- "ORCID login" cost: zero fees for a non-commercial individual-registered client; practical constraints are that credentials belong to one person's ORCID record (so a departing maintainer is a risk; mitigate by documenting re-registration), HTTPS-only redirect URIs that exactly match (so `api.yourdomain.org/auth/orcid/callback` must be registered verbatim), and the 100k reads/day quota (irrelevant for login-only use). Implementation in FastAPI: Authlib `OAuth().register('orcid', ...)` with ORCID's authorize/token endpoints, scope `/authenticate`, exchange the code server-side, and store the returned ORCID iD on the user. Use sandbox.orcid.org first.
- Session strategy: opaque, server-stored session IDs (>=128 bits) are preferable to JWTs because you need revocation (account deletion, abuse) and because OWASP's guidance is to keep session meaning server-side. Whether the ID travels as an HttpOnly cookie or as a bearer header depends on the frontend origin decision in Q5; either way the token is opaque and looked up in the DB.
- "Non-commercial" ORCID terms: a free, open research simulator qualifies; if the site ever sells access or runs ads, re-check the Public API ToS or become a member.

## Q5. GitHub Pages frontend calling a separate API: CORS, cookies vs tokens across origins, CSRF

### Takeaway
If the frontend stays on `<user>.github.io`, it is a different site from the API, cookies become third-party cookies (blocked by Safari/Firefox/Brave by default, user-controlled in Chrome, which abandoned deprecation in April 2025), so you must use header-borne bearer tokens with careful CORS; the cleaner fix is to put the Pages site on a custom subdomain of the same registrable domain as the API (e.g., `app.example.org` + `api.example.org`) so `HttpOnly; Secure; SameSite=Lax` session cookies work as same-site, with Origin checking and a custom header as CSRF defence.

### Cited Findings
- MDN Set-Cookie `SameSite`: `Strict` = "Send the cookie only for requests originating from the same site that set the cookie."; `Lax` = same-site plus cross-site requests that are "a top-level navigation" and use "a safe method: in particular, this excludes POST, PUT, and DELETE."; `None` = "Send the cookie with both cross-site and same-site requests. The Secure attribute must also be set when using this value."; "Some browsers use Lax as the default value if SameSite is not specified."; cross-site means "originating from a different site, including the scheme, from the site that set the cookie." — [MDN: Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)
- Public Suffix List: `github.io` is on the PSL, so `example.com` and `example.github.io` are "independent sites" and a cookie cannot be set on the public suffix itself ("it should not be possible to set a cookie on a public suffix (eg *.github.io, *.co.uk, ...)"). — [Atomic Object: Public Suffix List](https://spin.atomicobject.com/public-suffix-list/); [Haiku ticket #14810](https://dev.haiku-os.org/ticket/14810)
- Chrome third-party cookies: on April 22, 2025 Google announced it would keep the current approach and not roll out a standalone prompt; users "continue to make their own choice" in Chrome's Privacy and Security settings; this reversed the 2019 plan to phase out third-party cookies; in October 2025 several Privacy Sandbox APIs were retired while CHIPS and FedCM continue. Safari, Firefox and Brave block third-party cookies by default. — [Privacy Sandbox blog: Next steps](https://privacysandbox.google.com/blog/privacy-sandbox-next-steps); [TechRepublic](https://www.techrepublic.com/article/new-google-chrome-privacy-sandbox-third-party-ads/); [stape.io timeline](https://stape.io/news/google-chrome-cookie-deprecation)
- OWASP CSRF: the attack works because "browser requests automatically include all cookies including session cookies"; "A user-friendly defense that is particularly well suited for AJAX or API endpoints is the use of a custom request header"; "No token is needed for this approach."; "All modern browsers designate requests with custom headers as 'to be preflighted'"; warning that a permissive CORS configuration (e.g., trusting a takeover-able subdomain) lets an attacker "forge a request with your custom header"; "SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense"; "Stateful software should use the synchronizer token pattern", "Stateless software should use double submit cookies" with the "Signed Double-Submit Cookie" variant; "Consider verifying the origin with standard headers": if `Origin` is present "verify that its value matches the target origin"; "Missing headers and Origin: null are not evidence of a same-origin request." — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- OWASP Session Management: do not store tokens in localStorage/sessionStorage; prefer "HttpOnly; Secure; SameSite=Strict cookies (preferred) or a Backend-for-Frontend (BFF) pattern". — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- GitHub Pages supports custom subdomains via CNAME and apex domains via A/ALIAS/ANAME; verify the domain to prevent takeover. — [GitHub: About custom domains](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages)

### Inferences
- Option A (recommended): custom domain for both halves. `app.example.org` (GitHub Pages, CNAME) and `api.example.org` (your API). Because both share the registrable domain `example.org`, a session cookie set by the API with `HttpOnly; Secure; SameSite=Lax` (no `Domain` attribute, per OWASP) is sent on `fetch()` calls from the app because the request is same-site even though cross-origin; CORS must still allow origin `https://app.example.org` with `Access-Control-Allow-Credentials: true` and an explicit (never wildcard) allowed origin. CSRF defence: reject state-changing requests whose `Origin` header is missing or not in the allow-list, require a custom header (e.g., `X-Requested-With: sim`) on all non-GET calls so they are preflighted, and keep `SameSite=Lax` as defence in depth. This matches OWASP's preferred cookie-based model and avoids tokens in JavaScript-readable storage.
- Option B (if you must stay on `<user>.github.io`): the API is cross-site, so cookies would need `SameSite=None; Secure` and are third-party cookies that Safari/Firefox/Brave block by default; use opaque bearer tokens in the `Authorization` header instead. Mitigate the XSS-exposure OWASP warns about by keeping tokens short-lived in memory, rotating them via a refresh endpoint, scoping the SPA to a strict Content-Security-Policy, and never persisting tokens in localStorage. Bearer-header auth is not CSRF-able (the browser never attaches it automatically), so CSRF tokens are unnecessary, but CORS allow-list and Origin checks still matter.
- Public read-only API: allow `Access-Control-Allow-Origin: *` only on unauthenticated GET endpoints (run records, gallery, leaderboard), and serve them from a separate path prefix (`/v1/public/...`) so the permissive CORS policy never overlaps authenticated routes.
- Shareable run links: make `/runs/{run_id}` a public GET keyed by an unguessable ID (ULID/UUIDv7) with an explicit `visibility` flag; unlisted runs are reachable by link, public runs appear in the gallery; no auth cookie needed to view, so links work cross-site.

### Gaps
- MDN's glossary definition of "site" (registrable domain + scheme) was not fetched directly; the same-site inference for sibling subdomains follows from the PSL and SameSite semantics but should be checked against the MDN "Site" glossary page.
- GitHub's "Securing your GitHub Pages site with HTTPS" page returned 404 at the URL tried; HTTPS-on-custom-domain support is from prior knowledge and not cited here.

## Q6. Reproducibility and citability: run-record schema and patterns from research platforms (HF Spaces, W&B, OpenML, Zenodo/DataCite, Papers with Code)

### Takeaway
Credible platforms converge on the same provenance triple: exact code identity (git commit plus a diff/patch or snapshot for dirty trees, as W&B does), exact configuration/"setup" (OpenML flows + hyperparameters), and immutable, individually identified result versions (Zenodo version DOIs vs concept DOIs, Spaces as git repos). A run record that stores commit SHA, dirty flag + patch hash, lockfile hash, canonical scenario hash, seeds for every RNG stream, policy-weights hash, library/platform versions, timestamps and a content hash of the output, and that can be exported and deposited to Zenodo via its REST API (free, sandbox available, DOI pre-reservation) is what makes the backend citable.

### Cited Findings
- W&B `wandb restore` (docs now hosted at docs.coreweave.com): restores "Config (always): Write the run config to wandb/config.yaml", "Git (if available): Check out the original commit on a new wandb/run_id branch" and fetch/apply "any saved diff patch", "Docker (if available): If the run was executed inside a Docker container, start the same image with the original command"; must be run "from the same git repository as the original run". — [W&B CLI: wandb restore](https://docs.coreweave.com/models/ref/cli/wandb-restore); the Kempner Institute handbook: "When a run starts inside a Git repository, W&B automatically records the current commit", the client "captures the diff patch" of uncommitted changes, and `save_code=True` uploads a code snapshot (disabled by default). — [Kempner handbook: Reproducing W&B runs](https://handbook.eng.kempnerinstitute.harvard.edu/s5_ai_scaling_and_engineering/experiment_management/reproducing_runs.html)
- OpenML runs: "Runs are experiments (benchmarks) evaluating a specific flows on a specific task", linked "to the underlying data, flows, parameter settings, people, and other details"; "OpenML runs include all information needed to independently evaluate models"; "exactly reproducing all results may not always be possible" due to "changes in numeric libraries, operating systems, and hardware". — [OpenML: Runs](https://docs.openml.org/concepts/runs/); a "setup" is a flow with all hyperparameters set, and reinstantiating a flow "requires the same scikit-learn version as the flow that was uploaded" — [OpenML: Run setup tutorial](https://docs.openml.org/examples/30_extended/run_setup_tutorial/); given a run, the model can be rebuilt with `initialize_model_from_run`, but "you may need the exact same library version" — [OpenML: Flows](https://docs.openml.org/concepts/flows/); OpenML R client `runTaskFlow(seed=...)` "sets a seed to make the run reproducible" — [CRAN OpenML runTaskFlow](https://search.r-project.org/CRAN/refmans/OpenML/html/runTaskFlow.html)
- Hugging Face Spaces: "Spaces stores your code inside a git repository, just like the model and dataset repositories... Each time a new commit is pushed, the Space will automatically rebuild and restart." — [HF Spaces overview](https://huggingface.co/docs/hub/spaces-overview)
- Zenodo policies: "Total files size limit per record is 50GB" (higher quotas case-by-case); "Items will be retained for the lifetime of the repository", "currently the lifetime of the host laboratory CERN", with a programme "for the next 20 years at least"; "Data files are versioned. Records are not versioned."; "original content is never modified". — [Zenodo policies](https://about.zenodo.org/policies/)
- Zenodo versioning: "Versioning is used when you have updated the files of your published record"; a new version "is linked to all previous and future versions" and gets its own identifier; metadata-only changes are edits, not versions. — [Zenodo: Manage versions](https://help.zenodo.org/docs/deposit/manage-versions/); concept vs version DOI (secondary sources): Zenodo "mints a 'concept DOI' that always resolves to the latest version... while a version DOI points permanently to the exact files that existed at that version" — [dev.to: GitHub release to Zenodo DOI](https://dev.to/dmytronasyrov/github-release-to-zenodo-doi-265f); [CASRAI glossary: Zenodo concept](https://www.casrai.org/dictionary/term/zenodo-concept)
- Zenodo GitHub integration: once a repository is toggled on, "new releases from the repository will be automatically ingested and archived". — [Zenodo: Enable a repository](https://help.zenodo.org/docs/github/enable-repository/); metadata from `.zenodo.json` or `CITATION.cff` at the tagged commit (secondary) — [INBO checklist: GitHub/Zenodo/ORCID](https://inbo.r-universe.dev/checklist/doc/zenodo.html)
- Zenodo REST API: supports "upload and publishing of research outputs (identical to functionality available in the user interface)"; `prereserve_doi: true` reserves a DOI ("automatically generated by our system and cannot be changed", registered on publish); sandbox at sandbox.zenodo.org with "separate registration and separate access token" and test DOIs under prefix 10.5072; auth via personal access tokens with scopes such as `deposit:write`; rate limits "100 requests per minute, 5000 requests per hour" (search 30/min); base URL `https://zenodo.org/api/`. — [Zenodo developers](https://developers.zenodo.org/)
- Papers with Code: shut down in July 2025 (users cite July 24-25, 2025); Hugging Face's Trending Papers inside Daily Papers is a partial replacement for paper/code discovery, but "the full benchmark and leaderboard functionality is not replaced"; the data (18,000+ papers, 1,500 leaderboards, CC-BY-SA) is archived at paperswithcode/paperswithcode-data on GitHub. — [hyper.ai news](https://hyper.ai/en/news/42900); [CodeSOTA shutdown record (commercial third party)](https://www.codesota.com/papers-with-code/shutdown)
- Content-addressing precedent: Git stores each object "named with the SHA-1 checksum of the content and its header". — [Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

### Inferences
- Proposed immutable `runs` record (one row per execution; never updated after `finished`):
  - identity: `run_id` (UUIDv7/ULID, URL-safe, time-ordered), `parent_run_id` (for re-runs/replications), `created_by` (user id; store `orcid_id` when available), `visibility` (private/unlisted/public).
  - code identity: `engine_version` (semver of the simulator package), `git_commit` (full SHA), `git_dirty` (bool), `git_patch_sha256` (hash of the diff if dirty, patch stored as a blob), `lockfile_sha256` (uv.lock/requirements hash), `python_version`, `platform` (OS/arch), key library versions (numpy, torch/onnxruntime, simpy or equivalent) as JSON.
  - inputs: `scenario_id`, `scenario_sha256` (hash of canonical JSON: sorted keys, no whitespace, fixed float formatting), `params_json`, `policy_id`, `policy_weights_sha256`, `policy_format` (onnx/pt/npz).
  - randomness: `seeds_json` with one named seed per RNG stream (`sim`, `policy`, `env_noise`, `numpy_global`) plus the RNG algorithm name (e.g., `numpy.random.PCG64`); never a single implicit global seed.
  - execution: `queued_at`, `started_at`, `finished_at`, `worker_id`, `wall_seconds`, `status`, `error_text`.
  - outputs: `result_summary_json` (metrics used by the leaderboard), `result_blob_sha256` + `result_bytes` (full trace stored content-addressed), `schema_version` of the result format.
  - citation: `doi` (nullable; set when the user deposits the run bundle to Zenodo), `license`.
  Companion append-only `run_events(run_id, seq, ts, type, payload_json)` holds status transitions and progress ticks (the audit trail), and `scenarios`/`policies` tables hold the content-addressed inputs so identical inputs are stored once and a scenario hash in a paper resolves to exactly one object.
- Reproduce endpoint: `POST /runs/{id}/replicate` re-enqueues with the same commit/lockfile/scenario/seeds and records `parent_run_id`; equality of `result_blob_sha256` between parent and child is a machine-checkable replication claim, which is exactly the property W&B restore and OpenML `initialize_model_from_run` aim at but rarely verify automatically. Display a "bit-reproduced on <date> by <worker>" badge when hashes match, and show both hashes when they do not (OpenML's caveat about numeric libraries/OS/hardware explains legitimate divergence).
- Citability: (1) connect the simulator repository to Zenodo so each tagged release gets a version DOI and the project a concept DOI; store the release DOI alongside `engine_version` in each run record; (2) offer "Deposit this run to Zenodo" that uses the REST API (user's own token, sandbox first) to upload a run bundle (run record JSON, scenario JSON, seeds, result blob, environment lockfile, `CITATION.cff`) and writes the returned DOI back to the run row; (3) expose every run as `GET /v1/public/runs/{id}` JSON and as a human page with a "Cite" box (BibTeX with the run DOI if present, otherwise the release DOI + run URL + `result_blob_sha256`).
- Leaderboard/gallery credibility: rank only runs whose `git_dirty=false` and whose engine release has a DOI; label others "unverified build". Freeze leaderboard snapshots per engine release (OpenML-style per-task benchmarks), because a code change legitimately shifts scores.
- Papers with Code's closure removes the default external leaderboard venue for small research tools; hosting the leaderboard yourself, with the record schema above and CC-BY data export, is now the realistic path, and mirroring a static demo on HF Spaces (git-backed, free for static) gives the community-visible surface PwC used to provide.

### Gaps
- Zenodo's official pages on concept DOI vs version DOI and on `.zenodo.json`/`CITATION.cff` parsing were index pages without the details; those two facts rest on secondary sources.
- Did not fetch DataCite metadata schema docs; the recommendation to include `relatedIdentifiers` (IsVersionOf/IsDerivedFrom) is omitted for lack of a source.
- No primary source captured for Hugging Face Trending Papers' exact feature set.

## Q7. Rate limiting and abuse protection for a public simulation API

### Takeaway
Layer it: per-user job quotas enforced in the queue (the scarce resource is CPU-minutes, not requests), per-IP request limits in the app (`slowapi` with Redis/Valkey or in-memory), Cloudflare's free tier in front of the API for a single IP-based 10-second rate-limiting rule plus Turnstile (free, 20 widgets, works even if the site is not proxied through Cloudflare) on sign-up and anonymous "run" submission, and publish explicit quotas on the public read API the way ORCID and Zenodo do.

### Cited Findings
- Cloudflare WAF rate limiting by plan: Free = 1 rule, "IP only" counting, "10 s only" counting period and mitigation timeout; Pro = 2 rules, up to 1 min period, up to 1 h timeout; Business = 5 rules, IP and IP-with-NAT, up to 10 min period, up to 1 day timeout; Enterprise = 100 rules with headers/cookies/JA3-JA4/body characteristics. — [Cloudflare: Rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/)
- Turnstile: "Cloudflare's smart CAPTCHA alternative", "works without showing visitors a CAPTCHA", "can be embedded into any website without sending traffic through Cloudflare". — [Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/); Free plan: "Up to 20 widgets" per account, "10 hostnames per widget", 7-day analytics; Enterprise adds unlimited widgets, 200 hostnames/widget, "Any hostname widget", "Offlabel (remove Cloudflare branding)". — [Turnstile plans](https://developers.cloudflare.com/turnstile/plans/)
- `slowapi`: rate limiting for Starlette/FastAPI via the `limits` library with "redis, memcached and memory backends to track your limits (memory as a fallback)"; per-route `@limiter.limit("5/minute")`; "websocket endpoints are not supported yet". — [GitHub: slowapi](https://github.com/laurents/slowapi)
- Published-quota precedents for public research APIs: ORCID Public API "12 req/sec, 40 burst/sec" and "100k reads/day (per Client ID)", anonymous "25k reads/day (per IP address)". — [ORCID API client registration](https://info.orcid.org/documentation/integration-guide/registering-a-public-api-client/); Zenodo "100 requests per minute, 5000 requests per hour" for authenticated users, search 30/min. — [Zenodo developers](https://developers.zenodo.org/)
- OWASP: rate limiting is the named control against brute-forcing URL tokens ("Implement appropriate protection to prevent users from brute-forcing tokens in the URL, such as rate limiting"); uniform responses/timing to prevent account enumeration. — [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
- Capacity ceilings that abuse would hit on the cheap hosts: Railway Hobby egress $0.05/GB and per-second CPU/RAM billing — [Railway pricing](https://railway.com/pricing); Fly.io egress $0.02/GB NA/EU — [Fly.io pricing](https://docs.fly.io/about/pricing); Hetzner 20 TB included traffic with a monthly price cap — [Hetzner Cost-Optimized](https://www.hetzner.com/cloud/cost-optimized/); GitHub Pages 100 GB/month soft bandwidth limit — [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

### Inferences
- Quota model for the scarce resource: give each account a daily CPU-minute budget (e.g., N simulation-minutes/day, with a per-account cap on concurrent queued jobs), enforced at enqueue time by summing `wall_seconds` of today's runs; anonymous visitors get a small budget keyed by IP plus a Turnstile token on the submit form; researchers who sign in with ORCID/GitHub get more. Hard-cap single-run parameters (max simulated time, max agents) at the API so one request cannot run for hours.
- Request-level: `slowapi` per-route limits (auth endpoints tight, e.g., 5/minute on magic-link requests; public read API generous but bounded, e.g., 60/minute per IP), with a Redis/Valkey backend if you already run RQ, in-memory otherwise. Document the limits and return `429` with `Retry-After`, mirroring ORCID/Zenodo practice.
- Edge: Cloudflare Free in front of `api.example.org` gives one IP-based 10-second rule (useful only as a blunt flood stop) plus caching for public GET endpoints; since Turnstile does not require proxying, it works regardless. If finer limits at the edge matter, Pro ($20/month class) is the next step, which exceeds the budget; app-level limits are therefore the primary control.
- Abuse surfaces specific to this product: queue flooding (quota + concurrency cap), result-storage growth (content-addressed dedupe plus per-user storage quota and TTL for unlisted private runs), gallery spam (require a signed-in account with verified email/ORCID to publish to the public gallery; moderation flag), and bandwidth (serve large traces via object storage with signed URLs rather than through the API).
- Fixed-cost hosts (Hetzner, with a monthly price cap and 20 TB included) are safer against bill shock from abuse than per-second/egress-metered platforms (Railway, Fly), which is another argument for the VPS as primary host.

### Gaps
- Cloudflare's docs do not state explicitly that rate limiting on Free is unmetered; the plan table lists one rule on Free with no price column, and secondary sources describe it as free.
- No source gathered on hCaptcha/ALTCHA or proof-of-work alternatives; Turnstile was the only CAPTCHA option verified.

## Q8. Overall recommendation: one defensible stack for a solo-maintained research product, with fallbacks

### Takeaway
Primary: FastAPI + SQLAlchemy on SQLite (WAL) with Litestream to an S3-compatible bucket, one RQ worker (or a DB-polling worker to start) for simulations, `sse-starlette` for progress, Authlib for ORCID + GitHub login plus magic links, `argon2-cffi` only if passwords are offered, `slowapi` + Cloudflare Free/Turnstile for abuse control, all on one Hetzner CX23 (about €4.49/month) behind Caddy, with GitHub Pages on `app.<domain>` and the API on `api.<domain>` so HttpOnly same-site cookies work; every run stored immutably with commit/scenario-hash/seeds/weights-hash/lockfile-hash and exportable to Zenodo for a DOI. Fallbacks: Fly.io or Railway if you refuse to run a VM; Django + django-allauth if you want ORCID and passkeys with zero custom auth code; Neon Postgres when you outgrow one host.

### Inferences
- Why this is "serious" to researchers: the credibility comes from the data model and the DOI path, not from the hosting brand. Immutable run records with full code/seed/weights provenance, a public JSON API with documented quotas, a replication endpoint that compares output hashes, release DOIs via Zenodo's GitHub integration, and ORCID identities on runs are the same primitives OpenML, W&B and Zenodo use; a single €4.49 VPS running them is defensible.
- Why SQLite first: one host, one writer, read-heavy public traffic, trivial backups via Litestream, zero managed-DB cost, no scale-to-zero latency; the schema is plain SQLAlchemy so a later `pg_dump`-style migration to Neon/Supabase/self-hosted Postgres is mechanical.
- Why Hetzner over Fly/Railway: fixed monthly price cap and 20 TB traffic (abuse cannot create a surprise bill), real local disk for SQLite and result blobs, room for API + worker + Redis on 4 GB, no cold starts. Cost is operational: unattended-upgrades, Caddy for TLS, Litestream + weekly Hetzner backups/snapshots.
- Fallback ladder: (a) no-VM preference: Fly.io shared-cpu-1x 512 MB + 3 GB volume (about $4.14/month) with a second tiny Machine for the worker, or Railway Hobby with a 5 GB volume; (b) zero-dollar: Oracle Always Free A1 if capacity is available, accepting idle-reclaim risk (keep the worker busy or schedule synthetic load) and the reduced 2 OCPU/12 GB allocation; (c) auth-heavy: Django 6 + django-allauth (ORCID + GitHub + passkeys + email flows out of the box) with Django's Tasks API fronting an RQ/third-party backend; (d) scale: Postgres on Neon Launch (pay-as-you-go) when you need a second host or concurrent writers.
- Things that changed recently and invalidate older advice: Fly.io has no free tier (since Oct 2024) and bills snapshots from Jan 2026; Render's free Postgres is a 30-day trial; Oracle's Always Free Arm allocation is now 2 OCPU/12 GB; HF Gradio/Docker Spaces need PRO; Hetzner reportedly raised EU prices in April 2026; PythonAnywhere's $5 plan is gone ($10 Developer); `arq` is maintenance-only; Django 6.0 has a Tasks API but no worker; Papers with Code shut down (July 2025); W&B docs moved under CoreWeave; Turso is joining Supabase; Chrome kept third-party cookies (April 2025).

### Gaps
